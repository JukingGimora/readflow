# 给外部大模型的探索说明

这份文档是直接交给负责探索的大模型（或它背后的 code agent）看的。把它和 [`graph-spec.md`](graph-spec.md) 一起作为输入。

## 你的任务

用我给你的一个账号登录一个业务系统，弄清楚这个账号**能查到哪些数据、每种数据通过哪个接口取、接口怎么调**，然后交付一个符合 `graph-spec.md` 的 JSON 文件。

之后会有一个不具备探索能力的本地程序，完全按你的文件去登录、取数、回答用户的口头提问。它不会看页面，不会猜。**你没写清楚的，它就做不了；你写错的，它就答错。**

用户是不熟悉电脑的业务人员。他们原来要点三级菜单才能查到数，现在只想说一句话。

## 你会拿到

- 系统地址
- 一个账号（只用于本次探索，不要写进任何产出）
- 这个账号的角色说明（例如「供应商」）
- `graph-spec.md`

## 硬性规则

1. **只读。** 不点保存、提交、审批、删除、作废、确认收货、付款、导出、上传。不发 PUT / PATCH / DELETE。POST 只发列表和查询类请求。拿不准一个按钮或接口是否会改数据，就不要碰，记进 `not_queryable`。
2. **不外传数据。** 产出里不能出现账号、密码、cookie、token。样例里的人名、公司名、手机号、单号、金额要替换成假值，保留格式和字段名。
3. **不编造。** 每个接口必须是你真实调通过的；每个字段必须在真实响应里出现过。没验证过的不要写。
4. **控制频率。** 同一接口每秒不超过 1 次；翻页验证翻 2 页就够，不要把数据拉全。
5. **遇到验证码、短信码、滑块，停下来问人。** 不要尝试绕过。

## 操作步骤

**第 1 步：登录，记下登录过程。**
本地会照你写的 `auth` 自己去登录，所以要写到「照着做就能登进去」的程度：
- `login_url`：登录页地址。
- `steps`：账号输入框、密码输入框、提交按钮各自的 CSS 选择器；有验证码就写它的类型，图片验证码还要写图片和输入框的选择器、位数。选择器要在登录页上验证过只匹配到那一个元素。**不要把账号密码写进图谱**，本地会填用户自己保存的。
- `success`：登录成功后页面有什么变化（地址不再含什么、哪个元素出现或消失）。
- `session`：登录态放在哪（现在只支持 cookie；如果是放在请求头或浏览器存储里的令牌，在探索报告里写明，本地还取不走）；怎么判断过期（哪个接口返回什么）；`check` 填一个登录后一定能调通的只读操作。
- 滑块、扫码、短信、第三方登录：`steps` 里照实写 `challenge` 的类型即可，本地会让人在浏览器窗口里操作，你不用想办法绕过。

**第 2 步：拿到完整菜单树。**
优先找系统返回菜单的接口（通常登录后首屏就会调），拿不到再逐级展开页面菜单。每个叶子页面记录完整路径（一级 > 二级 > 三级）和路由。填进 `navigation`。**叶子页面要列全**，包括你后面判断为不可查的。

**第 3 步：逐个叶子页面，抓它调的查询接口。**
打开页面，打开浏览器的网络记录，点一次「查询」，再改一次筛选条件，再翻一页。对每个返回列表数据的请求，记录：
- 方法、路径、参数放在哪（URL / 表单 / JSON）
- 每个筛选条件对应哪个参数、什么格式（日期格式尤其要写清楚）
- 翻页用哪两个参数、每页最多多少条、总数在响应的哪个位置
- 列表在响应的哪个位置、怎么判断请求成功

**第 4 步：脱离浏览器重放。**
只带会话，用脚本直接调这个接口，确认能拿到同样的数据。**这一步过不了的接口不能写成 `http` 操作**：
- 请求里有前端现算的签名或加密参数 → 记为不可查，`gap: "G1"`
- 需要先从别的响应里取 token 或 id → `gap: "G7"`
- 明细要先查列表再逐条调详情 → `gap: "G5"`

**第 5 步：整理字段。**
把响应里的字段对上页面表头，得到中文名。判断类型（金额、日期、枚举）。枚举字段要列出所有取值：看筛选下拉框，不要只看当前数据里出现的。同一类数据在多个页面出现时，合并成一个 `entity`。

**第 6 步：写能力。**
对每个可查的页面想：**业务员会用什么话来问这里的数据？** 通常一个页面至少有两个能力：「合计多少」（带 `compute`）和「列出明细」。每个能力写：
- `slots`：能按什么条件问。接口支持的写 `to`，接口不支持但数据里有该字段的写 `filter: "local"`
- `examples`：至少 3 条，用口语，用菜单和表头上的词，要有不带时间的、带相对时间的（上个月）、带具体条件的
- `keywords`：用户说到这类业务时会用的词（书面的和口语的都要，例如「扣款」「罚款」「扣钱」）。本地先靠这些词判断用户在问哪一类，所以**不同页面的能力，关键词不要重叠**
- 条件怎么从话里取出来：枚举条件靠实体字段的 `values` 和 `synonyms`（把口语叫法、常见错别字都列进 `synonyms`）；单号、车牌这类编号要在 slot 上写 `pattern`（正则），否则用户报了单号本地也认不出来
- `followups`：答完之后人最可能接着问的 1–3 句
- `answer`：回答模板，一句话，先说结论

**第 7 步：自检，然后交付。**

## 交付前自检清单

能运行代码的话，先跑一遍校验器，它会逐条指出哪里不合格：`python -m qflow validate 你的文件.json`。一份能通过校验的格式示例见 [`examples/graph-example.json`](examples/graph-example.json)（虚构系统）。

校验通过后，对每个能力真实跑一次并和页面上的数字核对：`python -m qflow run 你的文件.json cap.xxx --params '{...}' --cookies 登录态文件`；再用几句口语试一下能不能对回正确的能力：`python -m qflow run 你的文件.json --ask "上个月扣了多少" --cookies 登录态文件`。它只执行只读操作。真实的一份见 [`../systems/sunner_srm/graph.json`](../systems/sunner_srm/graph.json)。

- [ ] 文件是合法 JSON，结构符合 `graph-spec.md`，所有 id 不重复、引用都存在
- [ ] 每个 `operation` 的 `access` 是 `read`，且都有 `evidence`（真实调通的时间、脱敏后的请求和响应样例）
- [ ] 用 `evidence` 里的响应样例，按 `rows_path` 和 `map` 能取出 `entity` 里声明的每个字段
- [ ] 每个 `capability` 的 `examples` 不少于 3 条，且任意两个能力的示例不会让人分不清该走哪个
- [ ] `auth` 里的每个选择器都在登录页上试过；`success` 在登录前不成立、登录后成立
- [ ] 每个能力写了 `keywords`；枚举字段写了 `values` 和口语叫法；编号类条件写了 `pattern`
- [ ] `navigation` 里每个叶子页面要么挂了 `capabilities`，要么写了 `not_queryable` 的原因
- [ ] 全文搜索不到账号、密码、cookie、token、真实人名和手机号

## 一并交付的探索报告（Markdown，一页以内）

- 探索用的角色、时间、覆盖了多少个叶子页面
- 可查 / 不可查 / 没来得及看 各多少个，不可查的按原因分组
- 你不确定的地方：哪些字段含义是猜的、哪些枚举可能不全、哪些接口行为有疑点
- 登录过程中哪一步需要人

不确定的地方**写出来**，不要为了让文件看起来完整而填一个猜的值。

## 不要做的

- 不要为了提高覆盖率把没调通的接口写进去
- 不要自己发明规范里没有的字段；需要的话写进探索报告，由人决定是否扩展规范
- 不要把一个页面拆成十几个只差一个筛选条件的能力；筛选条件用 `slots` 表达
- 不要写任何「怎么改数据」的内容，即使你看到了对应接口
